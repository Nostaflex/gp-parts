## 1. Pourquoi

L'admin actuel (`/admin`) est en mode **read-only démo**: boutons "Nouveau produit" / "Modifier" → toast "v2 Firestore". Aucun contenu géré dynamiquement par Stephane. Tout est hardcodé dans `lib/*.ts` arrays.

Stephane ne peut pas:

- Ajouter/retirer un véhicule de son stock
- Modifier un prix
- Voir les demandes de reprise reçues
- Tracker ce qui est publié sur Leboncoin

**Conséquence**: chaque mise à jour stock = ticket dev = redéploiement. Inacceptable pour usage production.

---

## 2. Vision

**Admin CMS** Next.js intégré, event-driven, qui permet à Stephane de gérer 100% du contenu mouvant en autonomie depuis `/admin`.

### Principes

- **Build-in admin** (pas de CMS tiers) — cohérent avec stack actuel Next.js + Firestore
- **Event-driven CRUD** — toutes mutations émettent events Firestore qui déclenchent side effects (cache invalidation, emails Resend, audit log, auto-draft Leboncoin)
- **Source de vérité Firestore** — `lib/products.ts`, `lib/vehicules.ts`, `lib/motos.ts` deviennent seeds initiaux, prod = Firestore live
- **DataAdapter existant respecté** — extension du pattern, pas réécriture
- **Photos Firebase Storage** — 5 GB gratuits, intégration native

### Non-objectifs

- Pas de CMS headless externe (Sanity, Strapi) — overkill et coût
- Pas d'event sourcing pur — events = side effects, pas reconstruction d'état
- Pas de workflow multi-utilisateurs (Stephane = solo admin pour MVP)
- Pas de versioning de contenu (history via audit log suffit)

## 4. Architecture événementielle

### Pattern event-driven adopté

```
┌────────────┐         ┌────────────┐         ┌─────────────────┐
│  Admin UI  │────────▶│ API Route  │────────▶│   Firestore     │
│ (Next.js)  │  POST   │ /api/admin │  write  │  (collection)   │
└────────────┘         └─────┬──────┘         └────────┬────────┘
                             │                          │
                             │ emit event               │ onWrite trigger
                             ▼                          │ (Firestore listener)
                       ┌──────────────────┐             │
                       │  Event Handlers  │◀────────────┘
                       └──┬───┬───┬───┬───┘
                          │   │   │   │
              ┌───────────┘   │   │   └────────────┐
              ▼               ▼   ▼                ▼
         ┌─────────┐    ┌──────────┐    ┌────────────────┐
         │ Cache   │    │  Email   │    │ Audit Log      │
         │ revalid │    │ Resend   │    │ (Firestore     │
         │ Path    │    │          │    │  immutable)    │
         └─────────┘    └──────────┘    └────────────────┘
                              │
                              │ + auto-draft
                              ▼
                       ┌──────────────┐
                       │ Leboncoin    │
                       │ /admin/lbc   │
                       └──────────────┘
```

### 4 side effects MVP retenus

#### A. Cache invalidation (Next.js `revalidatePath`)

- `ProductCreated` / `ProductUpdated` → `revalidatePath('/pieces')` + `revalidatePath('/pieces/[slug]')`
- `VehiculeCreated` / `VehiculeUpdated` / `VehiculeDeleted` → `revalidatePath('/vente-vehicule')` + `revalidatePath('/vente-vehicule/[id]')` + `revalidatePath('/sitemap.xml')`
- `MotoCreated` / `MotoUpdated` / `MotoDeleted` → `revalidatePath('/vente-moto')` + `revalidatePath('/vente-moto/[id]')` + `revalidatePath('/sitemap.xml')`

Implémentation: Next.js Server Action `'use server'` qui appelle `revalidatePath` après chaque write Firestore. Pas besoin de daemon externe.

#### B. Email notifications Stephane (Resend)

- `OrderPaid` → email confirmation client + email Stephane (déjà partiel)
- `DemandeReceived` (reprise/financement/contact) → email Stephane avec template structuré + lien admin
- `LowStockAlert` → email si produit pièce < seuil

Resend déjà configuré (`lib/email.ts`). Étendre templates dans `lib/emails/`.

#### C. Audit log immutable

Toutes mutations admin écrivent doc Firestore collection `audit_logs`:

```typescript
type AuditLog = {
  id: string; // auto
  timestamp: number; // unix ms
  actor: string; // email Firebase user
  action: 'create' | 'update' | 'delete';
  resourceType: 'product' | 'vehicule' | 'moto' | 'order' | 'demande';
  resourceId: string;
  before?: Record<string, unknown>; // snapshot avant (pour update/delete)
  after?: Record<string, unknown>; // snapshot après (pour create/update)
  ip?: string;
  userAgent?: string;
};
```

Read-only, jamais modifié. Page `/admin/audit` pour consulter avec filtres date/actor/type.

#### D. Auto-draft Leboncoin

- `VehiculeCreated` / `MotoCreated` → écrit doc dans collection `leboncoin_drafts` avec titre + description pré-générés (mêmes fonctions que `/admin/leboncoin` actuel)
- Page `/admin/leboncoin` affiche drafts auto-générés + drafts manuels
- Stephane copie-colle, marque "publié" → status `published`

### Firestore rules

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    // Lecture publique pour produits + véhicules + motos (catalogue site)
    match /products/{doc=**} { allow read; }
    match /vehicules/{doc=**} { allow read; }
    match /motos/{doc=**} { allow read; }

    // Écriture admin uniquement (token Firebase Auth + custom claim 'admin')
    match /{collection}/{doc=**}
      where collection in ['products', 'vehicules', 'motos', 'demandes',
                            'leboncoin_drafts', 'audit_logs', 'metadata'] {
      allow write: if request.auth != null
                   && request.auth.token.admin == true;
    }

    // Demandes: création publique (depuis form contact), lecture/update admin
    match /demandes/{doc} {
      allow create;
      allow read, update: if request.auth.token.admin == true;
    }

    // Audit logs: immutable (no update/delete même admin)
    match /audit_logs/{doc} {
      allow read: if request.auth.token.admin == true;
      allow create: if request.auth.token.admin == true;
      allow update, delete: if false;
    }

    // Orders: création publique (checkout), lecture/update admin
    match /orders/{doc} {
      allow create;
      allow read, update: if request.auth.token.admin == true;
    }
  }
}
```

## 6. Storage photos — Firebase Storage

### Structure buckets

```
gs://car-performance971.firebasestorage.app/
├── vehicules/{vehiculeId}/photo-{1..5}.webp
├── motos/{motoId}/photo-{1..5}.webp
├── products/{productId}/photo-{1..5}.webp
└── _uploads/                    # zone temp pour uploads en cours
    └── {uuid}.{ext}
```

### Workflow upload

1. Admin sélectionne fichier(s) image dans form CRUD
2. Client-side: redimensionne via `Sharp` côté browser (lib `browser-image-compression`) → max 2000px largeur, qualité 85, format WebP
3. Upload vers `_uploads/{uuid}.webp` via Firebase Storage SDK
4. Au save du form: copie vers `vehicules/{id}/photo-{N}.webp` + écrit URL publique signée dans Firestore doc
5. Cleanup `_uploads/` via Cloud Function trigger (ou cron, post-MVP)

### Storage rules

```
service firebase.storage {
  match /b/{bucket}/o {
    // Public read pour images catalogue
    match /vehicules/{vehiculeId}/{file=**} { allow read; }
    match /motos/{motoId}/{file=**} { allow read; }
    match /products/{productId}/{file=**} { allow read; }

    // Write admin only
    match /vehicules/{vehiculeId}/{file=**} {
      allow write: if request.auth.token.admin == true
                   && request.resource.size < 10 * 1024 * 1024  // 10 MB max
                   && request.resource.contentType.matches('image/.*');
    }
    // Idem motos, products...

    // Uploads temp: tout admin auth peut upload
    match /_uploads/{file} {
      allow write: if request.auth.token.admin == true;
      allow read: if request.auth.token.admin == true;
    }
  }
}
```

### Migration assets actuels

- Photo Racoon (déjà dans `public/images/`) reste local — pas dans Storage
- Logo SVG reste `public/images/` — pas dans Storage
- Photos placeholder Unsplash sur véhicules/motos: au premier save admin de chaque véhicule, Stephane upload ses vraies photos → remplace placeholder

## 10. Migration des données existantes

### Strategy

`lib/products.ts`, `lib/vehicules.ts`, `lib/motos.ts` deviennent **seeds initiaux**. Au premier déploiement:

```bash
GOOGLE_APPLICATION_CREDENTIALS=./service-account.json \
NEXT_PUBLIC_FIREBASE_PROJECT_ID=car-performance971 \
npx tsx scripts/seed-firestore-cloud-all.ts
```

Le script:

1. Lit `PRODUCTS` + `VEHICULES` + `MOTOS` arrays
2. Write to Firestore collections `products`, `vehicules`, `motos`
3. **Idempotent**: skip si doc déjà existe (ou option `--force` pour overwrite)
4. Log audit (action `seed`)

Ensuite, DataAdapter switche automatiquement: lit Firestore en prio, fallback aux arrays statiques si Firestore vide ou env emulator dev.

### Rollback

Si problème: Firestore Console > Export collection. Les arrays statiques restent committed dans repo, fallback safety net.

## 12. Risques + mitigations

| Risque                                                        | Probabilité      | Impact | Mitigation                                                                                  |
| ------------------------------------------------------------- | ---------------- | ------ | ------------------------------------------------------------------------------------------- |
| Custom claims Firebase Auth propagation lente (~1h après set) | Haute (one-time) | Bas    | User force re-login après set claim                                                         |
| Firebase Storage 5GB free tier dépassé                        | Faible           | Moyen  | Compression WebP + redimensionnement, monitoring quota                                      |
| Migration arrays → Firestore corrompt data                    | Faible           | Haut   | Script idempotent + Firestore export backup pre-migration                                   |
| Form contact `/api/demandes` reçoit spam                      | Moyenne          | Faible | Honeypot field + rate limiting middleware                                                   |
| Cache invalidation revalidatePath échoue silencieusement      | Moyenne          | Moyen  | Try/catch + log audit `revalidate_failed` event                                             |
| Stephane supprime véhicule par erreur                         | Moyenne          | Haut   | Soft delete (status `archived`) + confirm dialog double-clic + audit log restore via revert |
| Concurrent edits (Stephane + autre user dans le futur)        | Faible           | Faible | Firestore `updatedAt` timestamp + optimistic locking si conflit                             |
| Photos uploadées trop lourdes plombent CDN                    | Moyenne          | Bas    | Resize côté browser pre-upload (browser-image-compression)                                  |

## 13. Critères d'acceptation MVP

L'admin v2 est considéré MVP-shippable quand:

- [ ] Sidebar visible sur toutes pages `/admin/*` avec nav items + icônes + active state
- [ ] Stephane peut cliquer "Nouveau véhicule" sur `/admin/vehicules` → drawer s'ouvre depuis droite avec form vide
- [ ] Stephane remplit form + upload 5 photos → save → drawer ferme + ligne ajoutée dans table + véhicule apparaît sur `/vente-vehicule` dans les 5 secondes (cache revalidé)
- [ ] Click ligne véhicule → drawer s'ouvre avec form pré-rempli (mode edit) + URL devient `?edit=<id>`
- [ ] Stephane peut modifier prix, save, fichier `lib/vehicules.ts` jamais touché
- [ ] Escape ou X ferme le drawer, dirty check confirme si modifs non sauvées
- [ ] Bouton "Supprimer" → confirm dialog → soft delete (status `archived`) + véhicule disparaît liste publique
- [ ] Form contact site → demande créée dans Firestore + email Stephane reçu
- [ ] Page `/admin/demandes`: filtres status + type + recherche + click → drawer detail editable
- [ ] Audit log enregistre chaque mutation avec actor + before/after
- [ ] Photos uploadées resize <2000px avant upload (vérifier devtools network)
- [ ] Layout responsive: desktop sidebar 240px, tablet collapse 60px, mobile hamburger
- [ ] Tests E2E Playwright: create véhicule via drawer + soft delete + traiter demande
- [ ] Documentation `docs/admin-guide.md` lisible par Stephane non-tech avec screenshots sidebar + drawer
