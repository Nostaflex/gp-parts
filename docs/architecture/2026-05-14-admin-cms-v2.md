## 1. Pourquoi

L'admin actuel (`/admin`) est en mode **read-only démo**: boutons "Nouveau produit" / "Modifier" → toast "v2 Firestore". Aucun contenu géré dynamiquement par Stephane. Tout est hardcodé dans `lib/*.ts` arrays.

Stephane ne peut pas:

- Ajouter/retirer un véhicule de son stock
- Modifier un prix
- Voir les demandes de reprise reçues
- Tracker ce qui est publié sur Leboncoin

**Conséquence**: chaque mise à jour stock = ticket dev = redéploiement. Inacceptable pour usage production.

---

## 2. Vision

**Admin CMS** Next.js intégré, mutations-via-Server-Actions, qui permet à Stephane de gérer 100% du contenu mouvant en autonomie depuis `/admin`.

### Principes

- **Build-in admin Next.js** (pas de CMS tiers Sanity/Strapi/Payload)
- **Server Actions partout** pour mutations (validation Zod + audit log + revalidateTag dans même action transactionnelle)
- **Side effects synchrones post-write** (pas Cloud Functions — overkill pour MVP solo admin)
- **Source de vérité Firestore** — `lib/products.ts`, `lib/vehicules.ts`, `lib/motos.ts` deviennent seeds initiaux, prod = Firestore live
- **DataAdapter existant respecté** — extension du pattern, fallback statique uniquement en `NODE_ENV=development`
- **Photos Firebase Storage** — 5 GB gratuits, upload direct browser via SDK resumable
- **Auth whitelist email Firestore** (`meta/admins`) — pas custom claim (1-2 admins, simplicité > scalabilité)

### Non-objectifs

- Pas de CMS headless externe
- Pas d'event sourcing pur
- Pas de Cloud Functions Firebase (MVP solo, $5/mois Blaze plan non justifié)
- Pas de workflow multi-utilisateurs (Stephane = solo admin pour MVP)
- Pas de versioning de contenu (audit log suffit)

## 4. Architecture mutations (Server Actions + side effects synchrones)

### Pattern adopté

**Pas event-driven async**. Chaque mutation admin = Server Action transactionnelle qui exécute write Firestore + side effects **synchrones** dans la même request.

```
┌────────────┐   form submit   ┌──────────────────────────────┐
│ Admin form │────────────────▶│  Server Action 'use server'  │
│ (component)│                 │                              │
└────────────┘                 │  1. requireAdmin(uid)        │
                                │  2. Zod parse formData       │
                                │  3. Firestore tx:            │
                                │     - update entity          │
                                │     - insert audit_log       │
                                │  4. revalidateTag(...)       │
                                │  5. side effects (email,     │
                                │     auto-draft LBC)          │
                                │  6. return { ok | errors }   │
                                └──────────────────────────────┘
```

Pas de Cloud Function. Pas de queue. Pas de listener Firestore. Si side effect échoue (ex: email Resend down), on log mais on n'échoue pas la mutation.

### Side effects post-write (par type d'événement)

#### A. Cache invalidation — `revalidateTag` (pas `revalidatePath`)

Tag-based invalidation plus précis que path-based.

| Mutation    | revalidateTag                                                    |
| ----------- | ---------------------------------------------------------------- |
| `Product*`  | `revalidateTag('products')` + `revalidateTag('product:${id}')`   |
| `Vehicule*` | `revalidateTag('vehicules')` + `revalidateTag('vehicule:${id}')` |
| `Moto*`     | `revalidateTag('motos')` + `revalidateTag('moto:${id}')`         |

Côté pages publiques: `fetch(url, { next: { tags: ['vehicules', 'vehicule:${id}'] } })` pour bénéficier de l'invalidation.

**Note**: `revalidateTag` ne déclenche pas `generateStaticParams` → nouveaux véhicules ne créent pas nouvelles pages SSG automatiquement. Stratégie: ISR `generateStaticParams` lit Firestore au build, nouveaux véhicules servis via fallback dynamique jusqu'au prochain build.

#### B. Email notifications — Resend (existant)

- `OrderPaid` → email confirmation client + email Stephane
- `DemandeReceived` → email Stephane avec template structuré + lien admin
- `LowStockAlert` → email si stock pièce < seuil

Templates dans `lib/emails/`. Failures = log stderr, mutation continue.

#### C. Audit log immutable

Toutes mutations admin écrivent dans collection `audit_log/`:

```typescript
type AuditLog = {
  id: string; // auto-id Firestore
  timestamp: number; // unix ms
  actor: string; // email user authentifié
  action: 'create' | 'update' | 'delete';
  resourceType: 'product' | 'vehicule' | 'moto' | 'order' | 'demande';
  resourceId: string;
  diff?: Record<string, { before: unknown; after: unknown }>; // pour update
  expiresAt: number; // unix ms, +12 mois pour TTL Firestore native
};
```

**RGPD adaptation**: pour `resourceType === 'demande'`, on n'écrit **PAS** le `diff` complet (PII client). On garde seulement `{ resourceId, action, actor, timestamp }`.

**Coût**: ~50 mutations/mois × 1 write Firestore = négligeable ($0.18/100k writes).

**TTL**: Firestore TTL policy native sur field `expiresAt` purge automatique après 12 mois. Zéro Cloud Function cleanup.

#### D. Auto-draft Leboncoin

`VehiculeCreated` / `MotoCreated` → écrit doc dans collection `leboncoin_drafts/` avec titre + description pré-générés (réutilise fonctions actuelles `/admin/leboncoin`).

`VehiculeUpdated` → si draft existant avec `status === 'draft'`, regénère. Si `status === 'published'`, ne touche pas (Stephane gère).

### Security Rules (Firestore syntaxe valide)

```javascript
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    // Helper: user authentifié + email dans whitelist meta/admins
    function isAdmin() {
      return request.auth != null
          && exists(/databases/$(database)/documents/meta/admins)
          && request.auth.token.email_verified == true
          && get(/databases/$(database)/documents/meta/admins).data.emails.hasAny([request.auth.token.email]);
    }

    // Catalogue public en lecture
    match /products/{doc=**} {
      allow read;
      allow write: if isAdmin();
    }
    match /vehicules/{doc=**} {
      allow read;
      allow write: if isAdmin();
    }
    match /motos/{doc=**} {
      allow read;
      allow write: if isAdmin();
    }

    // Commandes: création publique (checkout), lecture/update admin
    match /orders/{doc} {
      allow create;
      allow read, update: if isAdmin();
      allow delete: if false;
    }

    // Demandes: création publique (form contact), lecture/update admin, delete soft-only
    match /demandes/{doc} {
      allow create;
      allow read, update: if isAdmin();
      allow delete: if false;  // RGPD: pas hard delete, status='deleted'
    }

    // Leboncoin drafts: admin only
    match /leboncoin_drafts/{doc=**} {
      allow read, write: if isAdmin();
    }

    // Audit log: immutable (no update/delete jamais)
    match /audit_log/{doc} {
      allow read: if isAdmin();
      allow create: if isAdmin();
      allow update, delete: if false;
    }

    // Meta: read seul admin (whitelist contient PII admin)
    match /meta/{doc=**} {
      allow read, write: if isAdmin();
    }
  }
}
```

## 6. Auth pattern (whitelist email Firestore)

### Pourquoi pas custom claim Firebase

- Custom claim = besoin Cloud Function ou Admin SDK script pour set + propagation 1h
- Whitelist email Firestore = 1 update doc pour ajouter admin, zéro Cloud Function

### Helper `requireAdmin()` côté Server Action

```typescript
// lib/admin/auth.ts
import { cookies } from 'next/headers';
import { getAuth } from 'firebase-admin/auth';
import { getFirestore } from 'firebase-admin/firestore';

export async function requireAdmin(): Promise<{ uid: string; email: string }> {
  const sessionCookie = (await cookies()).get('__session')?.value;
  if (!sessionCookie) throw new AdminError('Non authentifié', 401);

  let decoded;
  try {
    decoded = await getAuth().verifySessionCookie(sessionCookie, true);
  } catch {
    throw new AdminError('Session invalide', 401);
  }

  if (!decoded.email_verified) {
    throw new AdminError('Email non vérifié', 403);
  }

  // Check whitelist
  const adminDoc = await getFirestore().doc('meta/admins').get();
  const emails: string[] = adminDoc.data()?.emails ?? [];
  if (!emails.includes(decoded.email!)) {
    throw new AdminError('Accès admin refusé', 403);
  }

  return { uid: decoded.uid, email: decoded.email! };
}

class AdminError extends Error {
  constructor(
    message: string,
    public status: number
  ) {
    super(message);
  }
}
```

### Pattern Server Action

```typescript
'use server';

import { requireAdmin } from '@/lib/admin/auth';
import { VehiculeSchema } from '@/lib/schemas/vehicule';
import { revalidateTag } from 'next/cache';
import { writeAuditLog } from '@/lib/admin/audit';

export async function updateVehicule(prevState: unknown, formData: FormData) {
  const session = await requireAdmin(); // throws si pas admin
  const parsed = VehiculeSchema.safeParse(Object.fromEntries(formData));
  if (!parsed.success) {
    return { errors: parsed.error.flatten().fieldErrors };
  }

  const db = getFirestore();
  await db.runTransaction(async (tx) => {
    const ref = db.doc(`vehicules/${parsed.data.id}`);
    const before = (await tx.get(ref)).data();
    tx.update(ref, parsed.data);
    tx.set(db.collection('audit_log').doc(), {
      timestamp: Date.now(),
      actor: session.email,
      action: 'update',
      resourceType: 'vehicule',
      resourceId: parsed.data.id,
      diff: computeDiff(before, parsed.data),
      expiresAt: Date.now() + 365 * 24 * 60 * 60 * 1000, // +12 mois TTL
    });
  });

  revalidateTag('vehicules');
  revalidateTag(`vehicule:${parsed.data.id}`);

  return { ok: true };
}
```

## 9. Storage photos — Firebase Storage

### Workflow upload (browser-side compression direct)

1. Admin sélectionne fichiers image (input multi)
2. Browser compress via `browser-image-compression` (3M dl/sem, web worker, iOS Safari OK):
   - Max 2000px largeur
   - Qualité 0.85
   - Format WebP
   - Cap 25 MB par fichier (iOS Safari memory limit)
3. ID véhicule généré client-side avant save (UUID v4)
4. Upload direct via Firebase Storage SDK resumable (pas API proxy):
   - Path: `vehicules/{vehiculeId}/photo-{1..5}.webp`
   - Resumable = reprise auto si backgroundé Safari
5. Au save form: URLs publiques signées stockées dans Firestore doc

### Storage rules

```javascript
service firebase.storage {
  match /b/{bucket}/o {
    function isAdmin() {
      return request.auth != null
          && firestore.exists(/databases/(default)/documents/meta/admins)
          && firestore.get(/databases/(default)/documents/meta/admins).data.emails.hasAny([request.auth.token.email]);
    }

    // Public read pour catalogue
    match /vehicules/{vehiculeId}/{file=**} { allow read; }
    match /motos/{motoId}/{file=**} { allow read; }
    match /products/{productId}/{file=**} { allow read; }

    // Write admin only + limites
    match /vehicules/{vehiculeId}/{file=**} {
      allow write: if isAdmin()
                   && request.resource.size < 25 * 1024 * 1024
                   && request.resource.contentType.matches('image/(webp|jpeg|png)');
    }
    match /motos/{motoId}/{file=**} {
      allow write: if isAdmin()
                   && request.resource.size < 25 * 1024 * 1024
                   && request.resource.contentType.matches('image/(webp|jpeg|png)');
    }
    match /products/{productId}/{file=**} {
      allow write: if isAdmin()
                   && request.resource.size < 25 * 1024 * 1024
                   && request.resource.contentType.matches('image/(webp|jpeg|png)');
    }
  }
}
```

### Servir via next/image

Côté pages publiques (`/vente-vehicule/[id]`), photos Firebase Storage servies via `next/image` → cache Vercel CDN. Évite bandwidth Firebase Storage gratuit 1GB/jour bouffé par crawlers.

## 12. Risques + mitigations

| Risque                           | Probabilité | Impact | Mitigation                                                                               |
| -------------------------------- | ----------- | ------ | ---------------------------------------------------------------------------------------- |
| Custom claim refresh latence     | N/A         | N/A    | Pas de custom claim (whitelist email à la place)                                         |
| Firebase Storage 5GB dépassé     | Faible      | Moyen  | WebP compression + monitoring                                                            |
| Concurrent edits 2 onglets       | Moyenne     | Moyen  | If-Match pattern `updatedAt` + 409 conflict                                              |
| Photos orphelines                | Faible      | Faible | Upload direct path final (ID client-side)                                                |
| Stephane supprime par erreur     | Moyenne     | Haut   | Soft delete `status: archived` + ConfirmDialog double-step + audit log                   |
| Form contact spam                | Moyenne     | Faible | Honeypot field + rate limiting middleware                                                |
| revalidateTag fail silencieux    | Moyenne     | Moyen  | Log custom `[revalidate]` dans Server Action + monitoring drift `updatedAt` vs cache age |
| Firestore down → site casse      | Faible      | Haut   | Pages publiques utilisent ISR (cache last good) + fallback statique en development       |
| RGPD demande non traitée à temps | Moyenne     | Haut   | Tag email Stephane + reminder audit log expiration approche                              |

## Annexe — Anti-patterns à éviter (rappel review)

1. ❌ Middleware as security boundary → toujours re-vérifier authn dans Server Action
2. ❌ JWT en localStorage → httpOnly cookies (Firebase Auth SSR helper)
3. ❌ Types TS comme validation → Zod obligatoire frontière server
4. ❌ User-provided IDs sans authz check
5. ❌ `revalidatePath('/')` partout → over-invalidation perte ISR
6. ❌ Image upload sans cap → bloquer browser pre `Storage.put()`
7. ❌ Soft delete blanket → seulement où nécessaire
8. ❌ Custom claim sans force refresh → 1h "403 forbidden"
9. ❌ Firestore rules `where ... in [...]` sur path → syntaxe invalide
10. ❌ Audit log sans TTL → quota explosion + RGPD conflict
